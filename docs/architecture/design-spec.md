## 1. Scope and numeric conventions
Full backend release for the approved workflows, browser plus Android/iOS. Network connectivity is required for authoritative reads/writes and submission. Offline client storage/synchronization is externally owned; the backend neither stores live carts nor auto-submits work. There is no pilot-only functional reduction.
Design load is a test scenario, not a commercial limit: 100 organizations, 1,000 accounts, 100 concurrently active users, 50 vendors each at Pro's 5,000-product limit, 2,000 orders/day, 100 lines/order average, 10 million historical order lines. Test 50 requests/second sustained for 30 minutes and 100 requests/second for 5 minutes, including five simultaneous submissions/second. Actual adoption/date/budget are external inputs.
Quantities/minimum/step/counts: positive values 1..1,000,000,000 where positive is required; stock 0..1,000,000,000; delta signed integer including zero in that range. For every product, available count plus all outstanding pre-dispatch credit-eligible deductions must remain at most 1,000,000,000. Manual edits/reconciliation reject results exceeding this headroom; cancellation/rejection must always be able to credit original deductions. Dispatch releases the corresponding headroom. Use bigint intermediates and enforce the invariant under the inventory guard/balance locks. Maximum 500 distinct product lines/order or draft, 50 tiers/product, 50 tags/product, 1,000 explicit targets per promotion dimension. Reject entire over-limit operation. Price input maximum 999,999,999.99; computed order/report totals use exact NUMERIC(24,2), and checked overflow is a 422 error before any write. No IEEE floating point for monetary arithmetic.
Business text is plain text, NFC, trimmed at the ends; preserve internal whitespace and line breaks in descriptions/messages/notes, reject NUL and control characters other than LF/tab there. Names/reasons are nonblank; names disallow line breaks. Null clears only explicitly nullable fields; empty string does not masquerade as null. Existing code-point limits apply. Name uniqueness uses NFC + trim + Java Locale.ROOT lowercase, materialized as a database unique key; accent distinctions remain. PostgreSQL collation is not the uniqueness authority.
Email is trimmed and fully lowercased per prior approval, maximum 254 ASCII characters, one @, conventional dot-atom local part and DNS domain; no quoted local parts, international local parts, dot removal or plus removal. Do not perform SMTP probing. Passwords are never trimmed, NFC-normalized, logged or silently truncated; 15..128 Unicode code points including spaces. Business normalization does not apply to tokens/passwords.

## 2. Commercial interpretation and organization setup
Order prices/totals are **net goods amounts, exclusive of VAT**. The first release does not calculate VAT or generate fiscal/tax invoices. Return priceBasis=NET_EXCLUDING_VAT explicitly in quotes, orders and reports; tax is not implicitly zero. Vendor invoicing and statutory calculations remain outside this ordering backend. This is a selected product contract, not a legal compliance conclusion; jurisdictional review is a production gate (X-03).
Subscription APIs expose plan code, immutable revision, status and product/active-buyer limits. The [plan increment](../backend/trading/vendor-plans.md#implementation) uses organization_plan revision guards, one pending vendor request, real catalogue identity/archival and active trading usage, and explicit platform management reads. Actual direct changes supersede pending requests; current-revision no-ops preserve them. Retired targets cannot be newly applied, while assigned revisions remain pinned; setup retains its bounded invitation exception. There is no billing/price metadata field because no approved launch operation consumes it; no free-plan or zero-price claim is inferred. Adding billing later requires a new explicit contract. This resolves Q-SUB-004-E under delegation.
Organization country/type become immutable when authorized setup completes atomically with its first owner. Before completion, replace/revoke the setup invitation to correct country/type/recipient; no provisional business account is moved. Mistaken completed organizations are closed and replacement setup uses a distinct authorized account; this is not account reassignment or permission to bypass global current-email uniqueness.
Required organization data: displayName, legalName (1..200), country, type, registrationIdentifier (1..64 ASCII letters/digits/hyphen/slash), registered address, defaultLanguage. Optional taxIdentifier (same grammar). Treat identifiers as supplied business facts, not proof of incorporation or tax status. Unique normalized registrationIdentifier within country + organization type, including closed records. Same legal identifier may have separate buyer/vendor records. Platform support can correct a proven typo with an audit reason and collision check; it cannot change country/type or merge identities. Documentary verification is an operator task before setup invitations; no government-registry integration is included.
Organization states ACTIVE, SUSPENDED, CLOSED. Suspension is platform-admin-only with reason; all business sessions fail subsequent authorization, existing work/history remains, no automated cancellation/credit. Reactivation restores access without moving users. Closure is owner or platform admin, requires no nonterminal orders, disconnects links, invalidates invitations and sessions, retains commercial history. Closed organizations cannot reopen in ordinary APIs; exceptional mistaken closure is a reviewed data-recovery case, not a new membership endpoint.

## 6. Transaction and retry protocols
Global lock order: organization rows by UUID ascending; account rows by UUID; relationship; subscription assignment; vendor inventory control; product/unit/taxonomy rows by UUID; price/promotion guard; draft/import/quote; order/cancellation; stock balances by product UUID; sequence/replay/outbox. Commands lock only relevant rows but never acquire earlier classes afterward. Read/write authorization takes shared locks on actor account/organization; revocation takes exclusive locks in the same order. Changes affecting an entire vendor (tracking/catalogue terms/promotions/plan) coordinate through vendor guards; ordering locks shared guards, edits exclusive guards. This deliberately favors correctness at pilot scale.
Default Read Committed; reporting uses read-only Repeatable Read for a complete response (including optional counts). Ordinary lock timeout2s, statement timeout5s, total API deadline15s; reporting deadline30s; imports30s after preview (still2s per lock). Deadlock/serialization retries at most3 total with 25–75ms then75–150ms jitter, only within deadline and only definitely rolled-back work. No external I/O under business locks.
Quote review: POST reviews validates current lines/location/relationship and resolves all prices. Store a 15-minute review ID containing canonical submitted intent, location/contact snapshot, terms hash and buyer/vendor IDs. It reserves neither stock nor quota. Submission locks all current dependencies, recomputes and compares the reviewed commercial data; changes reject 409 TERMS_CHANGED with typed currentTerms (a fresh immutable OrderReview receipt for the same intent when still valid) and unavailableLines. The response never creates an order, deducts stock or consumes a draft; persisting this replacement validation receipt is the only allowed side effect of that rejection. Explicit user reconfirmation and a new submission referencing the returned receipt are required. If any line/location/relationship is now unavailable, currentTerms is null and safe typed issues identify the submitted line or delivery field without leaking inaccessible catalogue data; correct the intent and request another review. Never silently drop a line. Repeated rejected attempts may create expiring receipts but cannot create commercial effects. Stock changes alone recheck availability, not quoted price. Quote is bound to buyer, vendor, intent and, for draft submission, draft revision. Another same-org authorized member may submit a shared draft after reviewing it.
Order creation transaction: scope + permission + active domestic connection; buyer restriction; plan validity; active products/unit/base/quantity; reviewed terms; sorted stock availability; atomic all-line deductions; immutable party/delivery/pricing snapshots; vendor-local-year sequence; order/deduction records; consume draft if relevant; outbox; replay result; commit. Failure changes nothing. Number format YYYY/N, sequence starts1/year/vendor, no reuse, gaps acceptable. Optional replacement links only one direct successful replacement of a cancelled same-party order.
Cancellation/rejection atomically locks order, validates state/authority/reason, resolves pending cancellation request, transitions state, credits each originally deducted product once using unique credit identity, appends event and outbox. Tracking-off does not prevent original credits. Dispatch is rejected while cancellation request pending; approval/cancel/dispatch races serialize on order. Duplicate terminal transition replays its prior successful result only for the same command identity, not a contradictory new reason.
Stock absolute edits require expectedRevision; delta requires separate idempotency key, current balance lock and bounds. Zero delta and unchanged initialized absolute count return success/current count with unchanged revision and no stock-history entry; initial absent-count initialization is a real change. Store successful zero-delta replay so later retries do not become adjustments. Credit headroom is maintained even while tracking is off and for archived products. Deduction moves units from available to credit-eligible; cancellation/rejection reverses it once; dispatch removes eligibility, all in the same transaction. Manual adjustments do not erase obligations. Own-vendor stock responses expose cancellationCreditQuantity and maximumSettableCount for validation.
Reconciliation snapshots ALL vendor products, including archived products and absent counts, into server-owned preview rows; lifetime history is not capped by the non-archived plan limit. Preview metadata returns productCount/confirmedCount; lines are cursor-paged (25/default,100/max). Each line contains frozen source revision, proposed available count (zero if absent), outstanding credit quantity and acknowledgement state. PUT line batches of 1..100 unique products, with preview expectedRevision, explicitly acknowledge or update candidates; only preview rows change. Final confirmation sends preview expectedRevision and confirmAll=true, requires every snapshotted line acknowledged, locks/rechecks the entire current scope/source revisions/headroom, writes all counts and enables tracking atomically or changes nothing. An inventory generation changes on any product scope, stock, deduction/credit/dispatch-eligibility change, making an older preview fail409. No stock locks are held while a human reviews. Preview expires after24 hours; stale previews must be recreated. Page cursors bind immutable preview snapshot ID/source generation and product-ID ordering, not the mutable acknowledgement revision. Reading page1, acknowledging it and following nextCursor therefore succeeds while the source snapshot is unchanged. Batch/final writes still require the current mutable preview revision; any actual source inventory-generation change invalidates the entire preview. Archived products remain inactive and still require the approved stock confirmation before later reactivation.
Invitation accept and platform direct-connect lock vendor+buyer+relationship+plan, enforce country/caps, then create/activate once and close pending pair invitations. Duplicate pending create natural key is purpose/normalized recipient/target/context; return original. Resend uses separate key and increments generation/replaces token. Revoke/resend/accept serialize invitation; only current valid generation wins.
Idempotency keys only: direct no-draft submission, stock delta, new message, explicit invitation resend. Within one transaction acquire a nonblocking transaction advisory lock derived from full scoped key (collision merely causes temporary busy), then unique key row. Concurrent duplicate returns409 REQUEST_IN_PROGRESS; original payload match uses versioned canonical JSON after validation, preserving arrays/null/omission/revision. Store success body/status in same transaction. Unknown commit is checked by key on a fresh connection before any retrial. Never release a claim based only on caller timeout.
Successful response bodies expire after 7 days; retain key tombstones for the account lifetime, including operation, target and keyed payload digest, without full payload. Expired completed key returns409 REPLAY_EXPIRED; metadata does not authorize access. Natural identities (draft/import result, transfer acceptance, favorite desired state, order transitions) persist sufficient outcome references for object lifetime. Replays reauthorize current actor/object and issue fresh request/security headers.
Mutable reads return opaque revision = base64url of resource UUID plus monotonically increasing bigint, authenticated with HMAC-SHA256. Missing expectedRevision is422; wrong resource/forged/stale revision409; no-op preserves revision. Child edits bump their owning aggregate, not all organization records. No generic JSON Patch.
