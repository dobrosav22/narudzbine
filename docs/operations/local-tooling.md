# Local recovery exercise

Run `python BE/operations/verify_recovery.py` from the repository with Python3.9+, local Linux Docker, the pinned Temurin25.0.4.1+1 JDK and the Maven wrapper available. An explicit `--java-home` may locate that exact runtime. The runner refuses a remote Docker endpoint and an externally pinned recovery environment. It excludes inherited application/provider configuration. It creates only disposable synthetic PostgreSQL resources and never restores an existing environment or calls a hosted provider.

The command has a15-minute bound and runs the selected unit tests plus the real encrypted logical dump/restore scenario. It returns nonzero on infrastructure or verification failure; nothing is silently skipped. Its sole retained recovery artifact is `BE/target/recovery-contained-restore-evidence.json`: hashes, counts, lineage and measured times, without dump bodies or keys. Repeating creates fresh isolated resources; no production retry semantics are implied. Test lifecycle closes the contained application before its owned target database. On interrupted failure inspect the recorded owned resource identities; never remove unrelated Docker resources.

The scenario deliberately loses an acknowledged order and account deactivation after the backup. An independently verified daily archive is insufficient to reconstruct that interval. Successful restoration leaves ordinary access disabled, workers absent and private readiness503 while private liveness200. Restored role OIDs are not trusted. Neither this evidence nor a database-only elapsed time authorizes reopening or proves hosted PITR, immutable custody, key recovery, operator availability or reconciled RTO.

## Binary envelope command

The packaged Java entrypoint accepts only `--backup-envelope encrypt` or `--backup-envelope decrypt`. Supply process-scoped BACKUP_ENVELOPE_ISOLATED_KEY_ACKNOWLEDGED=true, BACKUP_ENVELOPE_KEY (base64 of a separately generated32-byte key) and BACKUP_ENVELOPE_CONTEXT (base64 of strict BackupContext JSON). Never place secrets in command arguments, tracked files or logs. Do not reuse export/archive/redaction keys. Known configured reuse is rejected; this cannot prove external key custody.

Context requires exactly version=1, UUIDv7 backupId, environment, non-URI sourceReference, numeric-string sourceClusterId, positive integer schemaVersion, postgresVersion=18.6 and UTC millisecond snapshotAt. Use independently measured source facts; never invent an identity. The canonical context and versioned header are authenticated with AES256GCM and a random96-bit nonce/128-bit tag.

The command reads binary stdin and writes binary stdout, without Spring, database, network or artifact publication. Maximum compressed plaintext is128MiB and metadata4096 bytes; excess is rejected. Decryption authenticates the entire bounded input before releasing any plaintext and requires adequate isolated process memory. Output failure can leave partial downstream output; restore only into a new empty disposable target using an atomic, error-stopping database restore. Encryption failure can leave partial ciphertext: publish create-only only after both upstream dump and envelope process succeed, then read-back verify its digest. Never treat a pipe's last exit status as proof that its producer succeeded. No cloud backup schedule or larger-dataset support is provided by this primitive.

## Recovery launch pin

OPERATIONS_RECOVERY_CONTAINED=true pins the restored process into containment. All25 registered ordinary/provider/worker/cleanup flags must remain false. A conflicting application property or enabled flag fails before ordinary bean construction. The private recovery health indicator keeps readiness DOWN even on a compatible restored schema. Scoped-redaction commands are rejected before credentials/storage/database access. An exact separately controlled --migrate remains possible; malformed command prefixes fail. No command here removes containment. RUN-03 reconciliation and a separately reviewed release remain required.


## Synthetic developer API

Run `python BE/operations/local_development.py check` for a bounded construction check, or `python BE/operations/local_development.py serve` for a fresh disposable API lasting one hour by default. For frontend development (D-GOV-007) three optional loopback-only inputs exist: `LOCAL_SYNTHETIC_SERVE_SECONDS` (60..28800), `LOCAL_SYNTHETIC_API_PORT` (fixed loopback API port, e.g. 18080, so the web dev proxy can target it) and `LOCAL_SYNTHETIC_BROWSER_ORIGINS` (extra exact https origins such as `https://localhost:3000`, still validated by the production origin policy). See FE/README.md. Use the same pinned JDK/wrapper/local Linux Docker prerequisites as recovery. No provider account is required. The runner compiles a test-classpath-only entrypoint; there is no fake-provider mode in the shipping JAR.

The READY line prints loopback API/management URLs and synthetic buyer/vendor/operator emails/resource IDs. Native login is POST /api/v1/auth/login with email, password="long synthetic password", transport="NATIVE" and a deviceLabel. That fixed password is an explicit test fixture and is never a production credential. Use the returned opaque bearer token only in local requests; do not copy tokens into evidence or tracked files. Browser/mobile client application work remains external.

Both countries have independent buyer/vendor organizations, an active connection, priced active product, unit, buyer location and a submitted order. A qualified synthetic platform operator has no business membership. A separate restricted worker automatically produces buyer/vendor portable JSON exports for both countries; the check verifies four actual requester downloads and platform denial. The in-app inbox worker (notifications.inbox.enabled) also runs, so order/message events reach the recipients' notification inbox within about five seconds; the check waits for each seeded vendor's ORDER_SUBMITTED notification. External email/push/provider delivery stays off. Provider doubles do not prove actual FusionAuth/Google/Apple/Resend/FCM/R2 conformance. Image processing/provider setup is verified separately by backend integration tests and is not a claim that every hosted service is available in this harness.

The UUIDv4 run identity labels the owned PostgreSQL container and names BE/target/local-development-<runId>.json. Evidence contains only synthetic IDs/emails, flags and route inventory; no passwords/tokens/keys/JSON export bodies. The runner checks freshness, run binding, the enabled inbox worker, four downloads,225 contracted operations and observed owned-DB cleanup. API, management and PostgreSQL bindings are asserted to be loopback. Each invocation creates new data and replaces no environment. Normal exit/shutdown closes workers/app before the owned DB. An interrupt (Ctrl+C) waits up to 120 s for the harness's own shutdown hook to do the same instead of killing the JVM, then reports whether the run-labelled database remains. The root `dev.py` runs this `serve` mode together with the frontend dev servers ([frontend overview](../frontend/overview.md#local-development-against-the-backend)). On interruption inspect only this run label; never delete unrelated resources.

## Local release rehearsal

Run `python BE/operations/verify_local_release.py --candidate <local-sha256-ID> --compatible-previous <local-sha256-ID> --incompatible-previous <local-sha256-ID> --output BE/target/local-release-evidence.json`. Inputs must be three distinct immutable local Docker config IDs, using the verified containment image and the documented pre-containment78/schema77 baselines for this rehearsal. Images must already exist locally; no registry promotion/deployment is performed. This is a synthetic rehearsal, not a general production rollback authorizer.

The script validates local Linux transport, reads packaged JAR identity/capability presence without starting unknown application arguments, and creates one internal disposable network/database. It verifies fresh/repeated/concurrent migration, unchanged unique successful migration history, ordinary startup of the same candidate under two local configs, prior schema78 readiness and schema77 rejection before HTTP. It refuses complete-release rollback to the old image because required recovery capabilities are absent. Preserve containment/fix forward; a database restore is a separate operation. A local config ID is never recorded as a registry manifest digest.

Commands have bounded subprocess waits and clean only exactly owned names. Nonzero exit means no passing claim. Source-provided secrets are never printed; generated DB credentials are ephemeral and passed only to owned containers. Repeat creates new state. The earlier prototype's incompatible-image liveness expectation was corrected to the actual fail-before-startup guard; failed logs remain in .tools. Hosted promotion, operator staffing, worker/data compatibility, provider conformance and every production release still require their own evidence and approval.

The workspace is read-only except backend target output. `--runtime host` retains the earlier host-to-Docker diagnostic path; do not mix its measurements with Linux results.

Actual resources/settings and before/after counters are recorded; no managed-provider plan or sizing is inferred. Synthetic load enables the normal60s core maintenance delay and verifies eligibility before measurements; ordinary JUnit retains its isolated fixture delay. Provider/stock flags and complete workload remain unchanged.

Metadata lives in `BE/target/local-load-<runId>.json`, `local-load-provenance-<runId>.json` and `local-load-resources-<runId>.jsonl`.
