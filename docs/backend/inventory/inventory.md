- Schema29 gives existing/new vendor organizations tracking metadata (off) and genuine product details absent-count balance metadata. Quota-only identities gain no count/balance; no count, event, completed confirmation or order is invented. getTracking/getStock never initialize quantities. Zero is an explicit initialized value. Counts apply across all vendor locations, with whole units only.
- Current owner/admin/staff use uniform EDIT_STOCK under the organization-first guard/actor/session order, including coherent reads and replay. Buyers/platform/foreign vendors cannot use these operations. Browser writes require CSRF/origin. Signed stock revisions bind balance revision and confirmation epoch. Stock edits work while tracking is off and for archived products; they do not enable tracking or activate products.
- Absolute writes require expectedRevision. Absent-to-zero is INITIALIZED, not a no-op. Delta needs an initialized count; zero delta/unchanged initialized absolute preserves revision/history/audit and cannot clear stale confirmation. Real set/delta confirms this product's current epoch. Explicit confirmation records CONFIRMED only when actually needed; absent count fails COUNT_REQUIRED. Archive/unit/pack changes invalidate product confirmation while retaining quantity/history; product scope/detail changes and stock effects advance the source inventory generation for later reconciliation.
- Available and cancellation-credit headroom use bigint intermediates and enforce available+credit<=1000000000, nonnegative, even while off/archived. Manual edits never erase credit obligations. Credits are zero because no actual order producer exists yet; synthetic credit fixtures test the invariant only. No order deductions/restorations/dispatch proof is claimed.
- Delta keys are strict single UUIDv4 Idempotency-Key headers, actor/operation scoped. Same key plus different own product/body conflicts; same normalized request returns its original success, including zero delta. Nonblocking transaction advisory lock derives from the complete scoped identity; collision/in-flight claim returns REQUEST_IN_PROGRESS. Nonlocking session snapshot admission identifies only the technical lock/throttle scope; shared session validity rules and final locked authentication/current authority still apply before business access.
- Absolute/confirmation replay uses actor/product/action plus complete normalized intent including expected opaque revision. This permits replay of an earlier no-op without consuming the unchanged revision for another new intent. Without a matching success, stale revisions reject with currentRevision. All successful effects, replay receipt, immutable stock event and audit commit together. Failure stores no success; retrying an uncertain delta must use the same key and inspect the replay result, never invent a new key. Replay is the original response; GET is current state.
- Success payloads last seven days; exact expiry fails REPLAY_EXPIRED. Internal compactExpiredReplay nulls expired payloads only, retaining immutable identity/scope/digest tombstones. No scheduled retention worker is claimed. History stores product/actor/time/before/after/delta/optional normalized reason, no failed attempts/no-op count events. INITIALIZED has before=null and delta=after; CONFIRMED has equal before/after and delta0. Audit has field names, not full reason.
- Own-vendor events use createdAt ASC/id ASC keyset pages, size25/max100, optional productId, no cross-page snapshot promise. Versioned signed cursors bind vendor/filter/page size/last tuple and24-hour expiry. Current signing key is identity.http.revision-key; optional inventory.cursor.previous-key and inventory.cursor.previous-until retain a previous cursor key only until an explicit instant no more than24 hours from configuration. Cursor rotation tests do not prove replay/revision-key rotation or production key operations.

Runtime additions: SELECT/INSERT/UPDATE on inventory_control and stock_balance; SELECT/INSERT on stock_event/stock_replay; UPDATE(original_result) only on stock_replay for expired-payload compaction. No stock/event/tombstone DELETE or event UPDATE. Product archive/unit/pack edits need balance/control UPDATE. Migration owner applies V20261019190000; readiness expects29.
