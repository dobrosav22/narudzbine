## Implementation

_Originally `BE/REPORTING_IMPLEMENTATION.md`: Business reporting refinement — 2026-10-20._

Selected under D-GOV-005, implementing D-STA-001–025 / D-PLAN-014 and DESIGN_SPEC §8. This records assistant implementation choices, not new user answers.

- Implement the three existing own-organization report reads. All active business roles may read summary/products; buyers report is vendor-only. No organization selector, location filter or platform support route is enabled by this batch.
- Current own organization/account/session guards are acquired in the normal writable authorization transaction. While those locks remain held, a separate read-only REPEATABLE READ transaction computes the entire report, including optional count. It takes no business locks and performs no writes. Successful session activity is recorded in the outer transaction. This preserves current authorization without weakening PostgreSQL read-only reporting. One nonblocking report slot per instance prevents reports exhausting the pool with outer transactions; concurrent reports receive503. The configured pool has10 connections and must retain at least2 plus capacity for ordinary traffic. Outer deadline30s, read-only transaction25s, existing statement5s/lock2s limits remain.
- Reporting owns explicit SQL read projections over frozen order/line data, latest order-event state and domestic connection/organization metadata. Identity depends only on reporting.api; reporting does not depend on another module's Java internals. No new schema or commercial write authority is needed.
- Summary requires DAY or MONTH. Tabular reports have no grouping parameter in the approved contract and use the same largest allowed horizon: at most60 inclusive calendar months. Summary DAY permits366 inclusive days; MONTH permits60 inclusive calendar months. Monthly periodStart is the first calendar day of that month, even for partial first/last months; only requested dates contribute.
- Delivered eligibility is latest committed order-event state. Frozen submission time selects the inclusive local-date interval; no current catalogue, price, unit or availability join. Latest eligible snapshot labels use submission descending/order UUID ascending within the requested range. Product sorting is quantity descending/product UUID ascending; buyer sorting goods total descending/buyer UUID ascending. Active zero-order buyer rows use current partner display name; qualifying history uses the latest eligible frozen buyer name. Disconnected zero-order rows are absent.
- Add explicit nullable activeBuyerCount to Report to expose D-STA-004: current active domestic connections for vendors, null for buyers. This is independent of the selected period; asOf covers the response snapshot. No current-state metric is inferred from delivered buyers.
- Aggregate values use exact decimal arithmetic and reject overflow beyond NUMERIC(24,2) or the contract integer maximum9,000,000,000,000,000 with422 REPORT_OVERFLOW. No payment, tax, fee or conversion calculation.
- Verification: real PostgreSQL totals/buckets/history, country/date/DST/limits, roles/current revocation, pagination/ties/zero rows, consistent snapshot across concurrent delivery, browser transport and default-disabled routing; focused checks then full wrapper and a distinct review. Exports remain a later batch.
