## Implementation

_Originally `BE/PASSWORD_IMPLEMENTATION.md`: Password lifecycle implementation._

Delegated refinements recorded 2026-10-18 before dependent code, under D-GOV-005 and D-PLAN-006/007/008/018. Backend only; approved password, session and recovery decisions remain binding.

- Three operations: requestPasswordReset, completePasswordReset and changePassword. Public requests acknowledge unknown, disabled and address-throttled addresses identically. Limits are three/address/hour and twenty/source/hour, including unknown addresses. Tokens are 32 random bytes, hashed, latest-only, single-use and expire at exactly thirty minutes. Proofs bind email, identity epoch and credential generation; deactivation/reactivation cannot revive them.
- A separate configured 256-bit reset-delivery key encrypts the short-lived delivery envelope with AES-GCM and proof-ID purpose binding. The proof table stores only its hash; the durable transactional email intent contains ciphertext, never a plaintext token. This producer is not a mail sender. VS-07 must validate eligibility/expiry again before decryption/rendering, then remove encrypted payload after delivery/expiry. No default key or production fake provider.
- Credential changes commit an operation record, pending barrier, epoch increment, session invalidation and transfer invalidation before the provider call. Provider writes are outside transactions and never automatically retried. Passwords exist only in request memory. Definite rejection releases the barrier but does not restore retired sessions; a new login is required. A write attempt consumes its reset proof even if the provider subsequently rejects it; a newly requested proof is required. Local shape validation precedes proof consumption.
- Successful reset revokes every session. Successful signed-in change retains the current session ID and absolute deadline, rotates its secret/CSRF, revokes other sessions and requires authentication less than five minutes old. If that session expires while the provider is executing, completion still commits and a fresh login is required. No retired-secret replay or credential response cache.
- Provider success is durably recorded before final completion. Completion, mandatory PASSWORD_CHANGED in-app/security record, queued email intent, credential generation and barrier release commit together. A failed final commit remains blocked and can be completed by subsequent login without repeating the password write.
- Uncertain writes remain blocked, including process loss after preparation. Reconciliation is read-only and requires positive evidence for this operation; absence of evidence never proves failure. The FusionAuth adapter atomically supplies a reserved user.data.narudzbinePasswordOperation marker with the password PATCH to the immutable provider user ID. A matching marker can confirm application, after which normal password verification is required before issuing a new session. G-02 must prove atomicity, marker protection, password validation/common-and-compromised rejection, Unicode/spaces, provider-session effects and absence of duplicate provider notices before real enablement. An unmatched/unreadable marker requires assisted provider investigation; neither login nor a new reset may blindly reissue the uncertain write. No automatic destructive repair or fabricated conformance evidence.
- FusionAuth API source: [Update a User](https://fusionauth.io/docs/apis/users/update) documents password updates and custom user data. Local adapter tests establish request/response handling only. No application MFA, automatic provider provisioning, purchases or production activation.

Schema14 adds operation/proof/encrypted-delivery records and extends mandatory notices for business and platform accounts while retaining ownership history. Runtime requires SELECT/INSERT/UPDATE on credential_operation and password_reset_proof, SELECT/INSERT on password_reset_delivery (payload cleanup will be separately granted to the eventual worker). Existing append-only notice/outbox/audit grants remain. Keys, markers and provider API permissions must be isolated by environment. Secret rotation must retain decryptability of unexpired queued intents or explicitly invalidate them and require a new request.

Positive read-only operation evidence permits local completion before fresh provider password verification; an old password cannot authenticate after reconciliation. Definite policy rejection releases the barrier without reviving sessions or claiming a PASSWORD_CHANGED event. Tests use controlled provider outcomes, not a real breached-password dataset/provider policy.
