## Implementation

_Originally `BE/EXTERNAL_IMPLEMENTATION.md`: External authentication implementation._

Delegated refinements recorded2026-10-18 before dependent code, under D-GOV-005/D-PLAN-006/007 and P1.1 REVIEW-01. Backend only. Six related operations cover LOGIN/LINK/REAUTHENTICATE, callbacks, native exchange, own identity listing and guarded unlink. No signup, email-based linking, organization switching or MFA.

- Add the already-selected Boot-managed security-oauth2-client starter, using Spring Security7.1.1 OIDC authorization-code authentication, token validation and Nimbus signature verification. Provider endpoints/issuer/client/callback/algorithm and exact return targets are explicit trusted configuration; no discovery from request data. Signed ID tokens, issuer, audience/authorized-party, expiry/issued-at, nonce and fresh authentication are checked before trusting subject. Provider email/user form data never selects an account.
- Five-minute hashed one-use state; independent backend PKCE S256 for provider exchange, nonce derived from its random verifier using a separate purpose. Encrypt only that short-lived verifier with a dedicated configured32-byte external-flow key and purpose/flow binding. No password, provider access/refresh token or application-session secret is persisted in a flow. State is consumed before the provider call, which runs outside transactions and is never automatically replayed on ambiguity/failure. A failed/lost callback requires a new flow.
- Browser starts require allowed Origin/JSON. LINK/REAUTHENTICATE additionally require the current session and CSRF; LINK requires recent proof again at final commitment. A separate Secure/HttpOnly __Host-narudzbine_oidc cookie uses SameSite=None for cross-site form_post and is bound to state; ordinary session cookies retain SameSite=Lax. The callback checks flow binding, provider and configured method. Temporary cookies can be replaced by a new flow; parallel tabs must complete the currently retained binding. No raw app-session token in a redirect.
- Native starts require a canonical S256 codeChallenge and configured ANDROID/IOS return target. Callback returns a separate hashed one-use60-second exchange code bound to that challenge. Exchange consumes it atomically with account/session/link effects, validates current epoch/generation and original session-token hash for link/reauth, and does not return provider tokens. Native clients must only exchange the code for their own initiated flow/verifier. Browser return is WEB only; native return targets are exact configured HTTPS app links.
- Provider issuer/subject identity is globally unique and permanently reserved to its original account, including after unlink. Relinking the same account reactivates that binding under a new security epoch; another account cannot claim it. Public LOGIN only accepts an existing active binding. LINK requires fresh current-account proof and fresh provider proof; successful local linking increments epoch/generation, rotates the retained current session with the new verified external method, revokes other sessions and invalidates prepared credential work. REAUTHENTICATE requires the provider identity already linked to that same account, rotates current session/method proof without extending its absolute lifetime. No remote credential write is required for these local binding operations.
- Unlink requires fresh proof specifically through a different still-usable verified method. PASSWORD proof requires a usable managed password; EXTERNAL proof requires a different active immutable binding. The last method cannot be removed. Successful unlink retains history, advances epoch/generation and revokes all sessions, requiring a fresh login through a retained method. Repeated unlink after fresh retained-method login is a no-op. No provider identity deletion or automatic recovery. Mandatory notices remain the approved event roster; external link/unlink is audited without inventing MFA events.
- G-02 must prove provider PKCE, nonce/fresh-authentication/subject mapping, Google/Apple client configuration, Apple form_post and client-secret rotation, return targets and no alternate signup/link path. Apple's primary authorization documentation does not establish PKCE support; do not silently omit it or claim compatibility. Real external-provider enablement requires explicit recorded conformance, default false; local fixtures are not that evidence. Apple client authentication uses a short-lived ES256 JWT generated from an explicitly configured isolated signing key. No actual keys/accounts/purchases/provisioning are authorized here.

Primary interface sources: [Spring OIDC authentication](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/oauth2/client/oidc/authentication/OidcAuthorizationCodeAuthenticationProvider.html), [Apple authorization](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.), [Apple token exchange](https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens). Provider conformance and external browser/mobile integration remain G-02/client gates.

### Configuration and schema16

Default activation remains off. Local synthetic fixtures use identity.http.enabled=true and identity.external.http.enabled=true, a dedicated Base64-encoded32-byte identity.external.flow-key, and exact HTTPS identity.external.return.web/android/ios targets without query/fragment. Real provider adapter activation additionally requires identity.external.provider.enabled=true and identity.external.provider.conformance=true **after recorded G-02 evidence**, never just to make startup pass. Google requires identity.external.google.client-id/secret/callback. Apple requires identity.external.apple.client-id/team-id/key-id/private-key/callback; private-key is Base64 PKCS8 EC P-256 supplied through isolated secret configuration, never committed. Callback paths are exactly /api/v1/auth/external/GOOGLE/callback and /api/v1/auth/external/APPLE/callback. Issuers, authorization/token/JWKS endpoints and RS256 ID-token algorithm are fixed in the adapter. Apple client assertion is ES256, five minutes, generated on demand. No discovery from user input.

Controlled migration V20261018180000__external_identities.sql advances readiness to16. Application schema15 rollback is incompatible; preserve data and fix forward unless a separately verified compatibility plan exists. Runtime needs SELECT/INSERT/UPDATE on external_identity, external_challenge and external_exchange; SELECT on managed_password_identity and column UPDATE(password_usable), plus existing session/account/transfer/audit/throttle grants. No DELETE/TRUNCATE/schema privilege. Composite identity/account foreign keys prevent cross-account session proof references. Immutable issuer/subject/owner and retained tombstones prevent reassignment. Challenges only transition OPEN→CLAIMED→COMPLETED; exchange only permits one consumed_at transition. Flow state/encrypted verifier and exchange metadata are retained; no runtime historical purge is introduced.

Managed credential binding now records password_usable, default true for existing mappings. External-only setup must insert its managed mapping as false; successful approved password RESET/CHANGE changes false→true only while its matching APPLIED credential barrier is held. Ordinary updates/deletion/rebinding remain rejected. VS-02 setup must provide the real managed subject and its actual usable-method state; none is fabricated by external login. An absent mapping cannot satisfy unlink's retained-password check.

Provider discovery reviewed2026-10-18: Google advertises S256; Apple does not advertise PKCE methods. Neither inspected discovery claim list proves the required fresh auth_time behavior. Strict backend verification remains in force. These are unresolved conformance checks, not an assertion that the providers do or do not support the full selected protocol. Follow [Google discovery](https://accounts.google.com/.well-known/openid-configuration) and [Apple discovery](https://appleid.apple.com/.well-known/openid-configuration) with actual registered-client sandbox evidence before activation.
