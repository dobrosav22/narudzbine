## Implementation

_Originally `BE/EMAIL_IMPLEMENTATION.md`: Login-email change implementation._

Delegated refinements recorded2026-10-18 before dependent code under D-GOV-005/D-PLAN-007/008/018. Implements request/read/cancel/mailbox-proof/complete as one backend batch; permanent account/organization identity, no MFA and P1.1 REVIEW-02 remain binding.

- Add required expectedRevision (current Account revision) to EmailChangeRequest. Account/revision plus normalized newEmail is the natural request identity: retries return the same request metadata, a different target with that identity conflicts, and a newly fetched account revision explicitly replaces pending work. No additional Idempotency-Key or arbitrary resend API. Creation requires authentication less than five minutes old. Completion independently requires fresh same-account authentication, current request revision, both proofs and an unexpired request.
- Both independent32-byte hashed mailbox proofs expire with the request exactly24 hours after creation and can be consumed once, in either order. Consumption only records verification/revision; it never updates login email or calls a provider. Proofs bind account email/security epoch/generation. Replacement/cancellation/epoch changes prevent revival. Terminal state projects EXPIRED or CANCELLED for expired/invalid pending requests without requiring a background worker.
- A global normalized email-claim registry backfills all current addresses, including disabled/platform accounts. Database account-insert/email-update triggers and request reservations use sorted email advisory guards after organization/account guards. Expired or epoch-invalid RESERVED claims can be reclaimed; IN_FLIGHT claims never expire until positively resolved. Current old email is released only in the completion transaction; reuse creates no account reassignment. Setup must use the same registry through the account trigger.
- Completion records EMAIL in the existing credential_operation journal, RECONCILING request state, frozen claim, account barrier/epoch, reset/transfer invalidation and revocation of other sessions before provider work. The original still-live session can only inspect its own pending email status or reconcile that same completion, with CSRF on mutations; it cannot access ordinary APIs or start another write. Successful email change revokes every session and requires new-email login, with no returned credential. This is a conservative delegated session choice; password-change retention remains unchanged.
- One remote email PATCH targets the immutable tenant/user and carries a reserved narudzbineEmailOperation marker. The backend then administratively verifies the primary address only after both local mailbox proofs. Uncertain PATCH/verification outcomes stay blocked; no automatic write retry. Read-only confirmation requires this marker, the intended verified primary email and no retained old-email alias. G-02 must establish those semantics, marker protection, former-address reuse, notification suppression and provider-session effects before real activation; an additional explicit default-false conformance flag gates this adapter. [Update User](https://fusionauth.io/docs/apis/users/update) and [administrative email verification](https://fusionauth.io/docs/apis/users/verify-email) are provider interface sources, not conformance evidence.
- Known provider success is recorded before atomic local completion. Account email/claim transition, credential generation, request state, all-session revocation, audit and mandatory EMAIL_CHANGED notice with distinct old/new delivery intents commit together. Failure leaves APPLIED plus the frozen claim/barrier; same-operation reconciliation or ordinary new/old-address login can positively confirm and complete locally before password verification, without repeating the remote write. Definite pre-write rejection cancels the request/releases reservation, but never revives sessions. Expiry prevents starting remote work; it cannot release an in-flight uncertain claim.
- Creation queues mandatory EMAIL_CHANGE_STARTED to the old address and encrypted proof intents for both mailboxes. A dedicated environment-isolated32-byte email-delivery key and email-change purpose binding protect envelopes. One in-app completion record has two explicitly pinned email destinations. Queueing is not rendering/sending; VS-07/G-04 must validate proof eligibility and pin first-rendered content, then clean expired/delivered ciphertext through reviewed worker migrations/grants. No email/provider purchase, provisioning, frontend implementation or production activation is included.

Schema15 extends existing credential/notice/outbox constraints while preserving password/ownership history. Runtime adds SELECT/INSERT/UPDATE on email_change/email_change_proof, SELECT/INSERT on email_change_delivery and SELECT/INSERT/UPDATE/DELETE on login_email_claim (deletion guard only permits stale/cancelled reservations or completed former-current release). Existing restricted grants remain; no runtime DDL/TRUNCATE. Recovery with no positive provider evidence remains assisted investigation, never an ad hoc barrier/claim clear.
