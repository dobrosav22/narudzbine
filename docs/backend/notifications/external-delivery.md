### Provider and possession boundary

FCM HTTPv1 sends a256-bit single-use random challenge through the configured isolated project to the exact token. The existing registerDevice POST gains optional paired verificationId/verificationCode fields. Without those fields a real verifier returns202 {id,expiresAt}; the code is delivered only through push data, never in HTTP metadata or logs. The client repeats POST with that code and the identical session/account/installation/platform/token. The challenge expires after120 seconds; at most3 unconsumed live challenges per account bound technical fanout. Committing registration consumes its verified challenge in the same transaction; unchanged successful registration retries can reuse its receipt, but removal/replacement prevents stale receipt reactivation. Cross-account takeover remains denied. A lost provider response does not cause automatic challenge resend: receipt of the unguessable code can reconcile it; otherwise wait for expiry and explicitly start again. A rejected project/token cannot yield a usable proof. Default missing provider configuration remains503.

Project send acceptance alone is insufficient proof of client possession. This extends the device foundation's opaque proof port without weakening it. Real FCM/APNs/web reception and environment isolation are empirical gates; local synthetic HTTP/device fixtures are not real conformance. Service-account OAuth uses explicit dedicated credentials and fixed Google endpoints, no ambient credential lookup; bounded2-second connect/10-second whole exchange, no redirects and bounded responses. No application MFA is introduced.

### Durable external work

Retained producer EMAIL/PUSH intents are authoritative source identities. An idempotent dispatcher materializes one email job or one push job per currently eligible installation; a permanent fanout receipt prevents repeated fanout. It never handles producer IN_APP rows. Current organization/account/role/preferences/destination/session/device authority is checked under normal organization/account guards before each external attempt. Technical proof/invitation content is resolved by an identity-owned port using its existing purpose-specific ciphers and current parent generation/expiry/issuer rules. Mandatory security notices bypass ordinary opt-out and retain explicitly recorded OLD/NEW destinations. Ordinary email destination changes terminate that old logical delivery rather than changing a Resend idempotency payload.

Workers claim at most50 candidates, one active job per task, with SKIP LOCKED,60-second lease and fresh attempt token. Four tasks per email/push channel; each provider call is bounded below the20-second heartbeat interval, so no long-running call requires heartbeat. Expired claim recovery is fenced; an old completion cannot change a newer attempt. Provider calls never hold database locks. Authorization is checked immediately before dispatch; already in-flight provider requests cannot be recalled after a concurrent revocation. Push is at-least-once, without an exactly-once claim.

Ordinary/necessary non-invitation deliveries have at most6 attempts at first attempt +0/30/120/600/3600/21600 seconds with deterministic per-job ±20% jitter, honouring provider Retry-After and FCM quota minimum60 seconds. Ordinary source lifetime24h. Email automatic retries stop before first attempt +23h, safely inside Resend's24h dedupe window; use the stable job UUID as provider Idempotency-Key and byte-identical frozen request. Invocations already claimed when a process dies are uncertain. Invitations, including invitation mailbox proofs, are never automatically retried after any attempted/uncertain send; source capabilities remain valid and explicit sender resend creates new work. Separate provider-accepted, mailbox-delivered, failed, suppressed, expired and unknown states remain observable. Invitation metadata projects its latest current-generation initial email job (not private mailbox-proof traffic); internal suppressed/expired maps to existing FAILED, without advancing business revision or changing original resend replay snapshots.

First attempt freezes locale/template/request in a dedicated AES-GCM delivery envelope. HTML parameters are escaped; generic subjects/visible push previews omit commercial/contact/message content. Ordinary payload/body retains the approved event type, organization identity and safe order reference (R-NOT-013), with authenticated opaque resource links; no amounts, excerpts or individual counterpart authors. Proof links use configured HTTPS client routes and URL fragments, not query logs; client handling remains external. Retries reuse the envelope while rechecking authority and destination. Terminal cached delivery bodies clear after7 days; minimal completion metadata remains. Physical source-token/metadata purge and legal holds retain their reviewed retention procedure, not an automatic destructive migration.

Resend callbacks verify the exact bounded raw body using Svix HMAC-SHA256 id.timestamp.body, constant-time comparisons,300-second clock tolerance and explicit current/previous signing keys. Deduplicate provider event IDs with payload digest, keep unknown-ID callbacks for out-of-order correlation, and update completion monotonically. ACCEPTED is not mailbox delivery; provider SMTP retries remain outside application control. Invalid/unregistered FCM feedback disables only the exact attempted device revision/token, preserving a concurrently refreshed token.

### Processing and failure interpretation

Source-transaction producer delivery rows remain immutable initial intents. external_fanout and external_job own external completion; inbox_work alone owns IN_APP completion. Never manually process/reset producer IN_APP rows, delete fanout receipts, change source IDs, or clear attempt counts to force a resend. Current-generation invitation reads project initial-email job state; mailbox-proof delivery remains private. ACCEPTED means provider accepted, not mailbox/device display. Signed email.delivered indicates Resend's mailbox handoff, not that a human read it. SMTP/provider retry behavior is separate.

The five-second driver runs at most one batch coordinator, with separate pools of4 email/4 push workers and at most50 claimed candidates per batch. It waits for outstanding tasks even when another fails, preventing duplicate queue accumulation. A provider exchange is bounded with2-second connect and <=10-second response/body deadline; FCM uses bounded OAuth refresh lock and shorter component deadlines. No provider call holds DB locks.60-second leases and fresh attempt fencing allow recovery; no long provider invocation exceeds the20-second heartbeat interval. Current authorization is checked before dispatch; in-flight requests cannot be recalled after a later revocation.

Ordinary/necessary non-invitation work retries at most6 times while source eligibility/expiry and Resend first-attempt +23h safety allow. The stable job UUID and encrypted frozen email request must remain unchanged across retry. Retry-After is honoured; FCM429 waits at least60 seconds. Push may duplicate after an uncertain send; no exactly-once claim. Invalid/unregistered feedback clears only the exact attempted device revision/token, so late feedback cannot disable a replacement. Data/notification preview is generic; permitted event/organization/order-reference fields and opaque authenticated links are separate from amounts/message bodies/personal counterpart authors.

Invitations/mailbox proofs make at most one automatic attempt. Failure/uncertainty or reclaimed expired SENDING becomes FAILED/UNKNOWN; do not resubmit it automatically, even if it might not have left the process. An authorized sender explicitly uses existing resends with its normal revision/key checks; that creates a new generation/source/expiry. Device verification likewise never blindly resends an unknown challenge: the app may acknowledge a received code or start again after120s. Challenge consumption and registration/audit commit together.

Read-only diagnosis: group external_job by channel/state, count expired leases, oldest QUEUED age, attempts/next_attempt_at/first_attempt_at and recent terminal counts; join source_kind/source_id only as needed under restricted operator access. Verify callback receipt IDs/provider references without selecting payloads, tokens, hashes, ciphertext, addresses or bodies. Queue state and fixed warnings are evidence of deferred work, not proof of provider delivery. Persistent oldest-work/UNKNOWN/final-failure counts require the named operator's monitoring/incident procedure; hosted alert routing/scheduling acceptance remains open.

After a lost database completion, ordinary email can reconcile by retrying the identical key inside its dedupe window. Unknown-ID callbacks are retained and correlated after acceptance using the same provider-reference guard. Never blind-retry beyond that window, rewrite the cached destination, move tokens between accounts, or infer success from an empty queue. Revoked account/session/device/current preference/role invalidates ordinary work; temporarily pending credentials defer it. Necessary proof emails additionally check their current parent/issuer/generation/expiry and dedicated cipher purpose. Recovery email acceptance does not replace independent operator proof of notice/challenge/registration facts.
