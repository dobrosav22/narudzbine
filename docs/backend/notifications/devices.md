## Implementation

_Originally `BE/DEVICES_IMPLEMENTATION.md`: Session-bound push registrations._

2026-10-20, delegated implementation refinement under D-GOV-005; preserves DESIGN_SPEC section9, R-NOT-012 and R-INF-014.

The existing three device operations use the current account/session and a server-selected environment/project. Registration requires a trusted verification port to establish project provenance and possession for the exact account/session/installation/platform/token digest, with a proof no older than60 seconds. A request's token syntax or environment assertion is never evidence. No production verifier is supplied by this batch: registration fails503 until one is configured. Fake verification proves local transaction behavior only; real FCM/app possession conformance remains G-04/G-07 work.

An environment/project binding is pinned in each database on first verified registration; a mismatched deployment cannot register copied production tokens. Installation identity and token digest ownership are retained; cross-account installation/token takeover returns409 without exposing the previous owner. Authenticated same-account registration may rebind an installation to its current session and replace its token, with stable resource ID and monotonic revision. Identical retries preserve revision. Changing platform on an existing installation conflicts. Possession-based cross-account recovery is deliberately unavailable until a separately reviewed proof flow exists.

Register and remove are browser CSRF-protected. All roles, including platform administrators, manage only their own registrations. Account/organization/session authority is reacquired after external verification; no provider is called inside a business transaction. A registry guard serializes token/installation claims after normal organization/account/session guards. Caps10 business/3 platform apply to currently eligible enabled installations; registration does not evict another installation.

Actual explicit registration/replacement/removal changes append an actor/device-only security audit in the same transaction; unchanged retries append none. No token/digest/envelope or installation identifier enters audit. Automatic revocation inherits its parent security action's audit; expiry cleanup retains device revision/disabled evidence.

Tokens are encrypted using a dedicated256-bit device key with resource-bound AES-GCM envelopes; digest/identity never appears in responses or logs. Disable/remove/revocation clears the token envelope atomically. Database triggers cover every session revocation path and account security-epoch/generation/state invalidation, including existing password/member/recovery writers. Natural-expiry eligibility is evaluated against current session/account/method state, never just the device flag. Minimal immutable ownership claims remain for safe retry/takeover denial; ordinary technical inactive token retention30 days is an upper bound, not a requirement to retain sendable secrets.

A minute scheduler clears up to100 expired/ineligible token envelopes with SKIP LOCKED, using injected Clock, even without provider credentials. Failure leaves work retryable and logs only a fixed warning. Database account-invalidation hooks use database statement time only for internal disabled-at evidence when the existing writer supplies no action timestamp; no expiry/business decision uses that timestamp. No session purge can delete retained ownership evidence by cascade.

Listing follows the existing offset contract, descending creation timestamp then ID; enabled means currently eligible, not merely stored intent. Removal is desired-state204 for an existing own registration,404 for foreign/unknown IDs. Re-registration explicitly re-enables; a removal retry never re-enables. Original IN_APP producer intents remain outside future external workers. Email/push delivery, real provider proof/credentials, invalid-token feedback and client permission/configuration are not claimed here.
