### Restricted private-case review entry point — 2026-10-22

Current BackendApplication has only the explicit --migrate early-exit command; other arguments start the normal server. A future operator command must therefore be deliberately recognized and fail closed on malformed operator arguments, with no accidental server/worker startup. Existing JdbcPrivacyCases.administrative reads only the metadata view and commits ADMIN_PRIVACY_CASE_READ; it does not authorize disclosure of the private request reason. JdbcAuditReads.platform always returns a NULL reason, so a new private review must preserve that generic audit redaction.

A raw database SECURITY DEFINER function returning private case fields in the same transaction that inserts its audit is insufficient as an independently audited operator interface: a direct SQL caller can receive the fields and then roll back the audit. Do not label that pattern audit-before-disclosure merely because the supported CLI commits before printing. Prefer a controlled application transaction/response boundary using current authenticated named operator authority, or explicitly design a committed, narrowly scoped access authorization before any restricted read. Any direct SQL principal mapping must prevent caller-supplied actor impersonation, role-name reuse and SET ROLE from changing the actual login identity. These are entry-point design constraints, not implemented permissions or a selected new public API.

The next implementation should be restricted private-case review first, with explicit operator qualification/configuration and reason/context audit, current revocation serialization, commit-before-disclosure failure checks and no commercial export/purge or fictitious case progress. Hold activation and assisted fulfillment follow only after their own enforcement and evidence are implemented. Real operator identity/credentials remain external inputs; no automatic mapping of every platform administrator or invented production account is authorized by this discovery.
