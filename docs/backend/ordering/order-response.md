## Implementation

_Originally `BE/ORDER_RESPONSE_IMPLEMENTATION.md`: Vendor order response refinement._

Selected under D-GOV-005 on2026-10-19 before dependent code. Implements acceptOrder/rejectOrder only, preserving D-ORD-006/010/011/012/016/017/025, D-ORG-024/026, D-CAT original-deduction credit rules and D-NOT-002.

Current vendor FULFILL authority and sorted party guards precede each command/replay; owner/admin/staff may respond, buyer/platform cannot. Existing open orders remain actionable after disconnection or buyer suspension; own current active authority is mandatory. Acceptance body requires expectedRevision and explicit nullable fulfillmentLocationId; null selects no location, never defaults. A selected active own-country vendor location is frozen with its full location projection and original opaque revision. No stage is assigned: acceptance contract has no stage input; stage administration/assignment remains separate. Buyer delivery and goods never change. Rejection requires normalized NFC/strip nonblank reason<=1000 code points, shared with the buyer in history but not external notice payloads.

Schema38 retains purchase_order and its submission snapshot unchanged. order_response is immutable natural command identity (order/from revision/action/original expected token/normalized location or reason), bound to a real appended response event. Existing revision1 event defaults stay untouched; response revision2 records previous AWAITING_ACCEPTANCE, actual vendor actor/time/reason and complete immutable response snapshot. Latest actual event snapshot supplies current detail/list/state; original keyed/direct and draft submission replay continue using the original creation snapshot. Current event projections show individual identity only to its own actor organization. No fake transition history. New response only accepts AWAITING_ACCEPTANCE revision1 and produces ACCEPTED or terminal REJECTED; future lifecycle migrations must explicitly extend this set.

Natural exact success is retained for object lifetime and may be reconciled by any currently authorized same-vendor member; original opaque expected token and normalized intent match before stale-revision/dependency revalidation. Different intent/action at the consumed revision conflicts IDEMPOTENCY_MISMATCH; a fresh current revision cannot repeat an invalid transition. Receipt references the immutable event snapshot, including original order/location response revisions, so key changes do not re-sign original successful bodies. No separate Idempotency-Key. Unknown outcomes require identical-body reconciliation; bounded definite-rollback retry follows existing order policy, never blind connection-loss retry.

Stock owner locks vendor control before the bounded order-lifecycle transaction advisory lock, then sorted product balances. Immutable purchase_order retains SELECT/INSERT-only runtime grants: PostgreSQL row FOR UPDATE requires UPDATE authority, so lifecycle serialization uses its explicit resource advisory lock plus existing pair guards, without granting immutable-header writes. Acceptance never deducts again or changes credit headroom. Rejection uses each actual immutable original obligation: only deducted=true lines receive a unique retained order_stock_credit and matching positive ORDER_CREDITED event. Add to available and subtract outstanding-credit quantity once even off-mode/archived/stale counts; preserve confirmation epoch/mode. No retroactive deduction/credit for off-mode original orders. Existing headroom makes restoration nonoverflowing; contradictory balances fail closed. Actual balance writes invalidate inventory-generation previews. SQL/deferred guards bind each credit/event to the actual rejection and require complete all-line credit state; any producer/commit failure rolls back response, balances, audit and notice intent.

Atomic status notice intent targets active verified original buyer submitter plus current buyer owner/admin, deduplicated; unrelated staff are not broadcast recipients. Event-scoped notice uniqueness preserves existing initial vendor notices. Existing three channel intents remain subject to future worker/current preferences (ordinary email/push default off); no provider send/purchase/workers introduced. Audit records actual action/time/actor and relevant changed fields/reason. Schema/runtime delta and actual verification must be recorded before handoff. Stage/cancel/request/dispatch/delivery/replacement and X/G/provider/client/full release gates remain separate.

Runtime audit_event remains INSERT-only; no new audit read grant or SECURITY DEFINER path is introduced. The mandatory audit producer shares the business transaction, with INSERT-denial rollback verification. Deferred SQL verifies response/event/credit/notice completeness using already permitted owner-table reads, rather than scanning protected audit records.

At equal millisecond event times, a response UUID is chosen after the previous event UUID in PostgreSQL canonical ordering, retaining UUIDv7 version/variant and actual event time. This is local order-event ordering, not a change to general resource UUID allocation. Timestamp random-space exhaustion fails closed; no fictitious later time is assigned.
