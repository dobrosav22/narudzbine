Retired stages may be renamed/reordered but never newly assigned. Reorder is a complete unique permutation of all retained IDs. Configuration rename/retire/reorder no-ops preserve revisions/audit; real changes bump configuration and affected stage revisions.

Explicit D-ORD-028/R-ORD-028 overrides the older DESIGN_SPEC sentence saying rename affects future assignments only: current order reads use the current stage label, without rewriting order snapshots/revisions or prior events. Exact original command responses keep their original frozen labels/tokens; GET returns current label. Transition events freeze previous/current stage IDs, labels as used at that transition and the configuration revision used. Rename/reorder/retirement does not move orders or rewrite historical labels. Current stage pointers survive retirement until the order progresses; entering any retired target fails.

Different intent conflicts, other creator/vendor404. Original signed response revisions are stored. Stage rename/retire/reorder use resource/configuration revisions; retain exact natural success for original expected token and normalized intent, reauthorize replay and preserve original response tokens. Stage assignment uses order/original expected token and target identity, permanent exact result; different target conflicts. No separate Idempotency-Key. Natural assignment receipts reference actual events for changes and retain a frozen result for no-ops; no fictional event is appended for no-op. No-op receipts include normalized intent in their identity and do not consume an unchanged revision: a different new intent at that still-current revision remains possible. A changed success consumes that revision; contradictory subsequent intent conflicts. Configuration mutation receipts use the same convention.

Order locks acquire vendor inventory control then stage configuration then existing order advisory and sorted balances, after pair/account/session guards; configuration commands never acquire order/balance locks afterward.
