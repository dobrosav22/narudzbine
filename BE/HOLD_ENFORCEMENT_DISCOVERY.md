## Candidate serialization protocol to verify before selection

A transaction-scoped PostgreSQL advisory barrier can separate authorization from disposal: disposal takes shared barrier access; hold activation/release takes exclusive access. Re-read applicable committed hold state in a separate SQL statement after waiting for the barrier; a single pre-wait snapshot must not decide preservation. Actual two-connection tests must prove activation-first blocks disposal and disposal-first completes or forces activation to retry its scope/preconditions. Review the complete lock graph before choosing the barrier position: existing organization/account/session/qualification guards must not be inverted, and activation must not take arbitrary source-row locks after a global barrier while cleanup holds those rows and waits for it. Any definite-rollback deadlock retry remains within the approved bounds; no uncertain commit is blindly retried.

For media, commit a destruction claim under the same shared barrier before external I/O. An exclusive activation must inspect all matching incomplete claims after acquiring the barrier; it cannot declare protected scope while an old claim may still call a provider. An expired lease is not proof the former worker stopped. Resolve from actual provider/worker evidence or remain pending/blocked; never mark success based on elapsed time. No provider call belongs inside a business transaction. A completed deletion before activation is an explicit preexisting loss, not content that a new hold can reconstruct.

This is a protocol candidate, not schema69 approval/implementation or a complete lock proof. The table/column/source classification, unclassified policy, exact supported hold scope, current qualification/reason/release events, access-expiry-versus-disposal behavior, and direct SQL/grant/trigger protection still need a recorded selection before code. Global preservation may be a conservative response for unclassified evidence, but its storage/retention implications cannot be hidden behind an organization-only label. Preserve existing business edits/history semantics and distinguish volatile credentials from evidentiary copies.


Primary references checked2026-10-22 for the candidate only: PostgreSQL18 [advisory/transaction locking](https://www.postgresql.org/docs/18/explicit-locking.html) and [function volatility/snapshots](https://www.postgresql.org/docs/18/xfunc-volatility.html). VOLATILE procedural functions take a fresh snapshot for each internal query; this supports the separate post-wait lookup proposal but does not prove this application lock graph or race behavior. Real disposable PostgreSQL tests remain required.


## Executed engine spike — 2026-10-22

.tools/hold-barrier-prototype.py tested the candidate on an isolated pinned PostgreSQL18.6 container with two synthetic tables and four actual concurrent schedules. Activation first made a waiting VOLATILE row trigger see the newly committed hold and reject disposal; disposal first made activation wait and see the already-removed synthetic payload; rolled-back activation allowed waiting disposal; release first let waiting disposal observe the committed release. Peers were synchronized from pg_stat_activity PgSleep after acquiring the relevant lock, not by assuming a sleep started the race. All four checks passed; the owned container was removed.

This is supplementary engine evidence only, outside the application's wrapper test totals. No application source/contract/schema was changed; it does not validate application source mapping, authorization, all lock order, storage bounds, external claims or real legal preservation. A selected production implementation still requires its own requirement-linked PostgreSQL/HTTP/migration/provider-failure/full artifact gates. No active hold or schema69 result is asserted.


## Static destructive-statement cross-check

A supplementary source search recorded86 candidate DELETE/NULL-bearing UPDATE statements across current Java sources (.tools/hold-destructive-statement-inventory.json). This is a discovery index, not86 executed tests or a complete SQL parser. Dynamic/multiline statements, database triggers and provider deletions require separate inspection.

The results include ordinary mutations as well as TTL disposal: shared favorite/draft-line replacement, gallery/tag/promotion targeting edits, volume-tier replacement, notification preference replacement and pending-cancellation transitions. Therefore a generic trigger on every DELETE or NULL transition would change approved business behavior. Classify each exact transition before selecting enforcement; preserve appropriate immutable historical evidence without inventing a blanket prohibition on legitimate edits. Commercial purge is already disabled; a future technical hold must state which evidence families it preserves and which ordinary source/history semantics remain relevant. Actual legal applicability remains X-03, not a conclusion from this search.

Replay/source families appearing in the search include contact/location/taxonomy/product/draft/promotion/export creation, message/order submission/order stage, stock/inventory lifecycle/pricing deactivation and privacy-case creation. Authentication families include pre-auth nonces/login attempts and claims/throttle buckets, setup registration/email claims, reset/email/setup/recovery deliveries/proofs, device verification, external challenge/exchange, sessions and push registrations. Notification/provider families include inbox sources/derived notifications, external jobs and callbacks; media includes raw upload/processed asset state plus external keys. Every selected family needs its own initial/retired/lifecycle/restore predicate and scope derivation check; the names alone do not confer permission to remove or retain data indefinitely.
