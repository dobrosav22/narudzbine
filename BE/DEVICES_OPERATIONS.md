# Device registration operations

## Schema52 extension

The [verified-delivery implementation](DELIVERY_IMPLEMENTATION.md) now supplies the gated FCM nonce verifier and external workers. [Current configuration/operations](DELIVERY_OPERATIONS.md) and [evidence](DELIVERY_VERIFICATION.md) supersede the absent-adapter statement in the historical schema51 increment below. Actual G-04/G-07 conformance and activation remain open.

Schema51 adds three existing own-account routes; authentication HTTP remains default off. The registration adapter is deliberately absent: POST fails503 without trusted project-and-possession verification, explicit server environment/project and a dedicated32-byte Base64 AES key. List/remove and local expiry cleanup have no provider I/O. [Refinement](DEVICES_IMPLEMENTATION.md), [grants](notifications/device-grants.sql), [contract](../openapi.yaml).

Configuration: notifications.devices.environment (lowercase environment name), notifications.devices.project-id, notifications.devices.encryption-key. Store each environment's key in its own secret store; never commit one. First verified registration permanently pins the environment/project in device_registry_guard. Restoring/copying a database into another environment must quarantine outbound work and reconcile this binding through a reviewed migration; do not change it with an undocumented console update or copy production provider credentials into staging. Real project provenance cannot be inferred from token spelling. A future verification adapter must establish exact possession/project proof, bound every proof field, emit verifiedAt at millisecond UTC precision, enforce a bounded provider timeout, and satisfy real-provider/client conformance before activation.

Apply the grant template as migration owner after controlled migrations, replacing only the validated runtime identifier. Session/account writers keep existing narrow grants; hardened SECURITY DEFINER triggers perform atomic invalidation without broadening those roles. Authenticated reauthentication rotates credentials on the same session and preserves devices; session revocation/account credential invalidation clears sendable envelopes. Explicit same-account re-registration restores a registration. Cross-account takeover is currently denied, even after removal; do not manually reassign a token or installation. Device resource IDs and minimal claims remain as ownership/retry evidence. A physical app used by a different account needs a separate installation identity and fresh provider token until a reviewed transfer proof flow exists.

The HTTP configuration's minute scheduler clears up to100 currently expired/ineligible envelopes with SKIP LOCKED; next tick retries failures, logging only a fixed warning. injected Clock drives eligibility and cleanup. Read-only diagnosis may count enabled/disabled registrations, missing envelopes and expired sessions in this environment without selecting ciphertext, token hashes or installation identifiers. Repeated failures require inspection of schema/grants/configuration; no blind provider retry or automatic cross-environment rebind. Removal and revocation clear token envelopes immediately, earlier than the30-day inactive-token upper bound. Session purge preserves disabled device identity rather than cascading it away. Physical assisted personal-data deletion/legal holds retain the existing reviewed procedure.

Key rotation needs a reviewed maintenance command that decrypts with the old key and re-encrypts under the new one, or explicitly disables registrations and requires re-registration. Such a command is not implemented here; never replace a live key and claim old envelopes remain usable. Future push sends must read current recipient preferences/role/session/device eligibility before every attempt, decrypt only within provider work, and fence invalid/unregistered feedback against the exact attempted token/revision so late feedback cannot erase a replacement. Those workers/provider adapters remain next work. Source IN_APP intents remain outside external delivery workers.

No provider provisioning/purchases, production release, real FCM/APNs/web permission proof, client integration, hosted scheduling/load or recovery conformance is claimed. Use [verification](DEVICES_VERIFICATION.md) for executed local evidence.
