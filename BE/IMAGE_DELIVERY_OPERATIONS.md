Backend/infrastructure only. No provisioning or release is authorized. Use [native preflight](NATIVE_PROCESSING_OPERATIONS.md) for the unchanged native worker. This schema49 delta supersedes its earlier content/24h-cleanup pending note.

Apply schema49 through the serialized migration owner; apply the reviewed [runtime grant delta](media/cleanup-grants.sql) with a validated existing role identifier. It adds cleanup events and the processed-deletion timestamp only. Existing upload/gallery/media reads, organization guards, source deletion and revision grants remain required. Native processing-role grants do not change. Do not give HTTP credentials READY proof writes or migration ownership.

The authenticated GET /api/v1/media/assets/{assetId}/content uses the explicitly configured private EU R2 adapter and has no separate public URL or provider presign flow. Storage remains disabled/fail-closed by default; identity HTTP enablement still gates the route. Four local concurrent bounded downloads and ordinary API throttling limit memory/provider work. Do not retry unknown upload/processing mutations by creating replacement identities automatically.

Optional minute cleanup is separately enabled with media.processed-maintenance.enabled=true (MEDIA_PROCESSED_MAINTENANCE_ENABLED). It owns scheduling independently of HTTP or processing enablement; leave disabled until database grants and real private-provider conformance are qualified. It considers25 oldest READY unreferenced candidates per sweep. Organization/asset/source guards recheck at least24h continuously unattached; attached images, including archived-product references, do not qualify. A permanent database claim blocks both downloads and attachment before provider I/O. Failed provider/commit outcomes retain the claim and original reference timer for reconciliation. A subsequent sweep retries it; never clear a claim, overwrite proof, resurrect DELETED or manually remove object markers.

Object removal uses HEAD/conditional zero-byte PUT/HEAD, never unconditional DELETE. Existing content requires If-Match of its observed ETag; an absent key requires If-None-Match:*. Existing valid tombstones are retained without rewriting. At most3 conditional conflicts reconcile per call; unknown response retains database work. Both processed and retained raw names are fenced before atomically recording DELETED/processed_deleted_at, missing raw deletion and immutable completion events. Completed processing jobs remain READY as historical processing evidence. Tombstones retain no customer bytes, but do retain storage identity and incur provider metadata/storage costs subject to budget gates.

Observe body-free database aggregates: READY with unreferenced_at older than24h; READY with cleanup_claimed_at; DELETED with processed_deleted_at; event counts by kind. A claim without completion may mean provider or database failure, not an absent object. The scheduler's Spring error handling records failures and continues later runs; investigate current aggregate age and provider errors before changing reviewed configuration. Do not log/download customer bytes, secrets or raw object addresses for diagnostics. Broad provider/monitoring performance and real recovery are still external gates.
