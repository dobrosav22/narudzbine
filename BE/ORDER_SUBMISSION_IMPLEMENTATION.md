# Direct order submission — implementation boundary

2026-10-19; delegated technical refinements under D-GOV-005, preserving D-PLAN-025 and approved order/stock/replay rules. Completed local batch; [verification](ORDER_SUBMISSION_VERIFICATION.md) records executed checks and remaining gates.

This batch implements submitOrder and getOrder. Direct submission accepts only a same-buyer unexpired receipt without a draft binding. Existing evaluation is reused for current pricing/delivery/availability. A commercial difference yields TERMS_CHANGED and a fresh receipt; unavailable intent yields null currentTerms and safe typed issues. These are normal transaction outcomes so the refreshed receipt can commit without any order, number, stock, audit or notice. Stock counts are availability checks, not held quote terms. Receipt IDs are not consumed for direct submissions: an explicit different key can intentionally submit another order.

A nonlocking identity-owned buyer routing projection admits the request but never grants business authority. The transaction first acquires a scoped nonblocking advisory key lock, routes via permanent replay metadata or buyer-scoped receipt, then locks both organizations in database UUID order before current account/session and SUBMIT permission. Replays reauthorize the buyer/current staff restriction, return the original success for seven days, and retain permanent minimal tombstones. Existing order access survives disconnection and counterparty suspension. Unknown commit is never blindly retried; a new request with the same key/body reconciles under the same advisory lock. Only definite rollback deadlock/serialization errors permit bounded retry.

Orders capture immutable party, delivery, line pricing, actor and initial event snapshots. Vendor-local calendar year numbers use transactional per-vendor/year counters; gaps are allowed and numbers are never reused. Snapshot detail is shared by the two parties; individual actor identity is exposed only to the actor's organization. Submission freezes ordered unit/pack identity and records each original stock effect. Tracked quantities move atomically from available to outstanding credit headroom; untracked lines retain an explicit no-deduction marker. Later dispatch/cancellation consumes this obligation; those actions are outside this batch.

New narrow owner ports: inventory OrderStock for submission deductions, notifications OrderNotices for durable new-order recipient/channel work, audit OrderAudit for business audit. Ordering may depend on these API packages and subscriptions VendorPlans, never implementation packages. Notification provider delivery/preferences and remaining workflow endpoints retain their later gates. The order producer queues all active vendor members for in-app/email/push; no provider call occurs in the business transaction. No fake replacement order is introduced; positive cancelled-order/replacement checks follow genuine cancellation history.

Acceptance: both countries/currency/local-year numbering; exact snapshots and buyer/vendor actor privacy; current permissions and staff restriction; changed terms/unavailable intent with no commercial effects; stock/no-stock and headroom; replay/mismatch/in-progress/expiry/response loss; competing stock/permission/terms changes; atomic failure including deferred commit; clean/previous migration, default-off routes and packaged artifact checks.

Review refinement before dependent code: the direct request contains only random UUID identities. Domain-separated SHA-256 fingerprints (actor/buyer scoped) remain stable across revision-key rotation; these are not password or customer-text digests. Store the original response revision token with the immutable initial order snapshot, returning it on submission/replay while detail reads use current signing configuration. Success expiry uses exactly604800 elapsed seconds, including DST transitions. Provider workers and future mutable order actions remain separate work.

Runtime JDBC sessions explicitly select UTC alongside existing statement/lock limits; Hibernate time-zone configuration alone did not govern JdbcTemplate session arithmetic. Elapsed expiry constraints remain timezone-independent. This is a reviewed local runtime configuration refinement, not a provider conformance claim.

Receipt reads acquire a transaction-scoped shared advisory lock before lookup; bounded expiry maintenance tries the same receipt lock exclusively and skips busy receipts. This prevents technical purge between valid checkout receipt validation and insertion, without granting UPDATE on immutable reviews or holding organization guards in maintenance. Expiry is still checked from the committing command time after authority acquisition.

Final configuration review: VendorPlans is an internal database owner port and must be available independently of the setup HTTP feature flag. Its JDBC implementation has no external/provider dependency, so it is instantiated in default-off startup too; HTTP controllers and committing authorization remain gated. Deferred lookup in ordering still fails closed if a required owner port is absent, never skips plan validation. This avoids making ordinary order submission depend on enabling invitation/setup endpoints.
