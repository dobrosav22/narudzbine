# External delivery operations

Schema52 and [grant template](notifications/delivery-grants.sql) are prerequisites; identity HTTP/device grants still apply. [Design](DELIVERY_IMPLEMENTATION.md), [evidence](DELIVERY_VERIFICATION.md), [client contract](../FRONTEND_HANDOFF.md). All provider, worker and callback flags default off. Real Resend/FCM/app/domain/environment conformance is G-04; web/Android/iOS acceptance is G-07. A configuration boolean records externally obtained evidence; it is not proof that checks ran. No purchases/provisioning or production activation is authorized by this implementation.

## Configuration and activation preflight

- FCM: notifications.providers.fcm.enabled, .conformance-verified, .client-email, .private-key-id, .private-key-pem. Explicit dedicated service-account PKCS8 RSA key from the correct environment's secret store. notifications.devices.environment/project-id/encryption-key must match the database's pinned project/environment. No ambient credentials, metadata endpoint or arbitrary provider URL. OAuth and FCM endpoints are fixed Google HTTPS endpoints. Actual isolated project/app registrations, APNs credentials, web permission/Service Worker setup and test-device receive/nonce acknowledgements are external evidence.
- Resend: notifications.providers.resend.enabled, .conformance-verified, .api-key. Explicit isolated provider account/key, verified sender domain and approved synthetic staging recipients. Fixed https://api.resend.com/emails, no SMTP fallback or redirects.
- Workers: notifications.delivery.enabled, .encryption-key (dedicated Base64-encoded32 bytes), .from (sender mailbox), .client-base-url (explicit HTTPS base, max512 characters; no userinfo/query/fragment). Never use unconfigured.invalid for activation. Identity HTTP supplies the device/technical-email ports; setup/recovery HTTP configuration supplies its purpose ciphers. Missing required ports/key/provider prevents worker activation. A technical parent whose optional purpose configuration is absent stays unsent with a fixed warning; do not bypass this check.
- Callback: notifications.email-webhook.enabled, .secret (whsec_ provider signing secret), optional .previous-secret and .previous-secret-valid-until. Previous secret acceptance lasts no later than24h from configuration and ends at the exact configured instant. Clear old configuration after rotation. Endpoint POST /api/v1/provider-callbacks/email requires identity HTTP's public route boundary; it ignores business cookies and validates exact raw bytes before JSON. Never configure a business-account bearer token as callback authentication.

Before enabling a provider/worker, verify owned account/project/domain/app identifiers and budget authority, apply controlled migration/grants, confirm destination environment binding with read-only queries, provide isolated secrets, execute actual G-04 sandbox error/dedupe/callback/receive tests, and capture their truthful results. Staging cannot use production registrations or credentials. No live messages should be sent as an undocumented readiness test. Core database readiness does not imply provider readiness. External worker flags do not enable the separate notifications.inbox.enabled scheduler; full notification acceptance must configure and verify that worker independently. Never enable verbose JDK/provider wire/header/body logging with live credentials. Missing domain/client routes/operators remain X-01/X-02/X-05/X-06 inputs.

## Processing and failure interpretation

Source-transaction producer delivery rows remain immutable initial intents. external_fanout and external_job own external completion; inbox_work alone owns IN_APP completion. Never manually process/reset producer IN_APP rows, delete fanout receipts, change source IDs, or clear attempt counts to force a resend. Current-generation invitation reads project initial-email job state; mailbox-proof delivery remains private. ACCEPTED means provider accepted, not mailbox/device display. Signed email.delivered indicates Resend's mailbox handoff, not that a human read it. SMTP/provider retry behavior is separate.

The five-second driver runs at most one batch coordinator, with separate pools of4 email/4 push workers and at most50 claimed candidates per batch. It waits for outstanding tasks even when another fails, preventing duplicate queue accumulation. A provider exchange is bounded with2-second connect and <=10-second response/body deadline; FCM uses bounded OAuth refresh lock and shorter component deadlines. No provider call holds DB locks.60-second leases and fresh attempt fencing allow recovery; no long provider invocation exceeds the20-second heartbeat interval. Current authorization is checked before dispatch; in-flight requests cannot be recalled after a later revocation.

Ordinary/necessary non-invitation work retries at most6 times while source eligibility/expiry and Resend first-attempt +23h safety allow. The stable job UUID and encrypted frozen email request must remain unchanged across retry. Retry-After is honoured; FCM429 waits at least60 seconds. Push may duplicate after an uncertain send; no exactly-once claim. Invalid/unregistered feedback clears only the exact attempted device revision/token, so late feedback cannot disable a replacement. Data/notification preview is generic; permitted event/organization/order-reference fields and opaque authenticated links are separate from amounts/message bodies/personal counterpart authors.

Invitations/mailbox proofs make at most one automatic attempt. Failure/uncertainty or reclaimed expired SENDING becomes FAILED/UNKNOWN; do not resubmit it automatically, even if it might not have left the process. An authorized sender explicitly uses existing resends with its normal revision/key checks; that creates a new generation/source/expiry. Device verification likewise never blindly resends an unknown challenge: the app may acknowledge a received code or start again after120s. Challenge consumption and registration/audit commit together.

Read-only diagnosis: group external_job by channel/state, count expired leases, oldest QUEUED age, attempts/next_attempt_at/first_attempt_at and recent terminal counts; join source_kind/source_id only as needed under restricted operator access. Verify callback receipt IDs/provider references without selecting payloads, tokens, hashes, ciphertext, addresses or bodies. Queue state and fixed warnings are evidence of deferred work, not proof of provider delivery. Persistent oldest-work/UNKNOWN/final-failure counts require the named operator's monitoring/incident procedure; hosted alert routing/scheduling acceptance remains open.

After a lost database completion, ordinary email can reconcile by retrying the identical key inside its dedupe window. Unknown-ID callbacks are retained and correlated after acceptance using the same provider-reference guard. Never blind-retry beyond that window, rewrite the cached destination, move tokens between accounts, or infer success from an empty queue. Revoked account/session/device/current preference/role invalidates ordinary work; temporarily pending credentials defer it. Necessary proof emails additionally check their current parent/issuer/generation/expiry and dedicated cipher purpose. Recovery email acceptance does not replace independent operator proof of notice/challenge/registration facts.

## Secrets, retention and recovery

Rotate provider credentials through reviewed environment configuration; never paste key material into logs, planning or tests. Encryption keys must be retained for existing envelopes. Live delivery/device key rotation requires a reviewed decrypt/re-encrypt command or explicit disable-and-reregister procedure; no such automatic key rotation is supplied here. Raw request bodies, provider bodies, access tokens, proof links and signing signatures must not enter logs. Driver failures emit only a fixed warning. HTTP exchanges use explicit service credentials without ambient identity discovery. Subscribe the Resend endpoint only to outbound email delivery events (sent/delivered/bounced/complained/failed/delivery_delayed), not incoming-email/domain events.

Terminal rendered cache clears after7 days. Expired challenge/source proof30-day hash/token and external metadata/callback90-day physical purge with legal holds remains assisted reviewed retention work; this batch does not claim legal deletion. Preserve permanent fanout/source ownership identities until that procedure defines safe reconciliation. Before any restore/release, freeze outbound work, preserve attempt/provider references and apply the existing uncertain-window containment/reconciliation runbook; restored QUEUED/SENDING is never proof a message was not already sent. No automatic destructive recovery or production release is authorized.
