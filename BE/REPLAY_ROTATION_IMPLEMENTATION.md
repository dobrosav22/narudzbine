# Targeted retry compatibility under signing-key rotation

2026-10-19; delegated refinement under D-GOV-005. Completed local batch; [verification](REPLAY_ROTATION_VERIFICATION.md) records execution and remaining gates.

Keep existing stock HMAC domains/bytes and permanent records unchanged. Introduce identity.http.replay-fingerprint-key, independent of revision signing. During controlled schema35 cutover, explicitly set it to the original revision key used to create historical stock replay records. A singleton immutable database fingerprint binding rejects a missing/changed key after adoption; first adoption with historical stock or resend receipts requires the explicit configuration. Empty installations may initially adopt the current revision key, but must pin that value before later signing-key rotation. No raw secret is stored in PostgreSQL. Unknown/multiple historical keys require reviewed recovery and known-request evidence; never infer a key, rehash/delete tombstones, or silently execute again.

This is a long-lived replay compatibility key, not a login/authentication credential. Ordinary revision/cursor rotation must not change it. Replacement of this compatibility key requires a separately reviewed versioned migration preserving permanent tombstone recognition; no ordinary blind rotation or deletion is supported. The startup guard deliberately fails closed on accidental replacement.

New stock success receipts retain their original signed revision alongside the internal item snapshot; legacy receipts reconstruct the original token using the pinned legacy key. Fresh GET uses current signing configuration. Invitation resend identity already uses sender/invitation/raw UUID and its original expected revision string; preserve its original signed result revision too, with the same legacy cutover fallback. Direct orders already have stable domain-separated UUID digests and frozen response revision. Messages have no producer yet; do not claim their verification. No API/business change, new retry key, frontend or provider action.

Acceptance: reproduce the old duplicate; new and schema35 legacy stock successes/tombstones survive rotation without a second effect; original body/status and mismatch/expiry/current authority/concurrency/failure behavior; invitation resend original response and no additional delivery under rotation; binding startup admission/missing key/mismatch/immutable guards; previous-schema migration and full/artifact gates. Natural resource-creation fingerprints using revision keys are audited separately: stable resource IDs prevent duplicate creation, but rotation may affect their payload/revision-token compatibility; retain an explicit follow-up rather than claiming all natural-action replay is solved by this targeted batch.
