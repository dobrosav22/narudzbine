# Exceptional recovery implementation

Delegated refinements recorded2026-10-18 before dependent code under D-GOV-005/D-PLAN-008/025, D-ORG-052 and R-SEC-037. Four operations cover evidence-case creation/read, distinct administrator review and intended-account acceptance; no commercial support writes, impersonation, user reassignment or MFA.

- Cases are immutable-intent client UUIDv7 resources. Creator/normalized original payload replay returns original metadata for seven days; mismatched intent conflicts, other creators cannot reuse the ID; retain tombstone. Active named platform administrator and current session/CSRF are required, including replay. Fresh authentication is required for create/review. Target is an existing business member of the supplied original active organization; platform-account recovery is outside this business-evidence contract.
- Capture original owner/target security epoch/generation, organization owner pointer and creator/reviewer security epochs; later account/owner/security changes permanently invalidate unstarted cases. No role/state reactivation. OWNER targets must be active verified existing non-owner members. EMAIL retains original account/organization; authenticated acceptance cannot reactivate a disabled member. The former owner need not supply a live session; database owner invariants remain in force until the atomic change. Pending remote credential work blocks mutation.
- EvidenceReference is an opaque restricted operator-system reference, not uploaded evidence or a boolean approval. A consuming RecoveryEvidence port checks registration/requester/independent contact/notice/challenge facts outside transactions. It must return notice completion time and no unresolved challenge for this exact immutable case; actual implementation, evidence channels and named accountable operators are X-05. No production adapter or synthetic auto-approval is installed. Local controlled fixtures exercise this boundary. Review rechecks current case/reviewer/version after inspection; second administrator cannot be creator. Rejection is terminal; approval pins reviewer and attestation. Acknowledged evidence must be complete and notice time must be canonical millisecond UTC, >= case creation and <= now.
- Notices to target and former owner old contacts are durable necessary transactional delivery intents; queuing does not prove notice. Approval derives notBefore=confirmed notice time+24h and acceptance expires exactly seven days after notBefore. Unreviewed cases expire eight days after creation; review does not silently extend repeatedly. A later successful security/owner change invalidates prepared authority even if it returns to its prior value.
- Approval creates a purpose-encrypted, hashed single-use acceptance token, delivered only to the target account (OWNER) or proposed new mailbox (EMAIL). Tokens never appear in admin/API case responses or logs. Token possession plus <5-minute current same-account authentication is required after notBefore and before expiresAt. Admins cannot accept on a user's behalf. Repeated committed acceptance requires fresh target authentication and the original token, never repeats effects or clears a fresh cookie.
- Owner acceptance atomically updates owner pointer/roles (former owner becomes DEACTIVATED ADMIN), epochs/generations, all affected session revocations, pending proof/transfer invalidation, mandatory OWNER_CHANGED/RECOVERY_COMPLETED notices, audit and case state. No ownerless interval or organization change. Current authority serializes on organization then sorted account identities then session/case rows.
- Email acceptance stages an ordinary guarded email-change record with an explicit recovery association, claims its target under the existing global address guard, and never treats evidence as an old-mailbox proof. The old-mailbox verified flag remains false; the exceptional case explicitly authorizes bypassing that proof. The new-mailbox flag records the acceptance token delivered to that address. Ordinary completion cannot use this bypass. Final case/token/reviewer/freshness checks and consumption join the existing PREPARED EMAIL barrier transaction. The original session may only reconcile that operation while pending; unknown outcomes never redispatch the provider write. Positive ordinary-login reconciliation can finish it. Email/provider/local claim/session/audit/notices and RECOVERY_COMPLETED/case completion commit together. Expiry or reviewer changes before dispatch deny; after authorized dispatch ambiguity must be resolved without undoing the credential barrier. Definite provider rejection terminates the case. Unstarted staged changes remain subject to ordinary claim expiry/cancellation and cannot execute via the public email-completion endpoint.
- Default recovery HTTP activation is off. Enablement requires an explicit evidence-port implementation and a dedicated32-byte recovery-delivery encryption key. No provider provisioning, real evidence certification or real mail delivery is claimed. Schema17/grants are recorded below; executed evidence is in [verification](RECOVERY_VERIFICATION.md).
