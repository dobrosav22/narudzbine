# Shared draft submission refinement

Selected under D-GOV-005 on2026-10-19 before dependent implementation; preserves D-BUY/D-API natural identity and reviewed P1.1.

POST /api/v1/drafts/{draftId}/submission accepts reviewId and expectedRevision and returns200 Order. Current buyer submission authority, browser CSRF and sorted buyer/vendor guards precede every execution/reconciliation. No Idempotency-Key. Any currently authorized same-buyer submitter can reconcile the exact successful request; immutable draft identity/review/original opaque expected revision binds the result for object lifetime. A different request after consumption conflicts IDEMPOTENCY_MISMATCH; GET draft exposes submittedOrderId. Original token is retained without re-signing/revalidating after signing-key changes. Expired/purged reviews and disconnected/suspended counterpart do not invalidate successful reconciliation. Own current authority remains mandatory.

New execution requires OPEN draft/current revision, unexpired same-draft numeric revision and exact saved intent. Shared order production reuses current terms, plan, snapshots, numbering, stock obligations, audit and notice transaction. Changed terms persist only a fresh review bound to the unchanged draft/revision; unavailable intent has typed safe issues. Neither outcome consumes draft. Success links one real order, advances draft revision once and appends SUBMITTED attribution while preserving intent/lines. Terminal work cannot edit/discard. Distinct direct-keyed submission still rejects draft receipts.

Schema37 extends direct-only order guards with an explicit nullable draft source and permanent immutable draft_order_submission identity. Deferred checks require exactly the appropriate direct or draft receipt and a reciprocal terminal draft/order/event binding plus all existing stock/line completeness checks. Existing OPEN/DISCARDED records and direct orders remain unchanged. Buyerworkspace owns consumption through its API; ordering owns commercial success. Providers are outside this transaction. No fulfillment/cancellation/credit/provider/client implementation is implied.

Verification scenarios: both countries, shared members, exact original reconciliation after expiry/purge/disconnection, stale/edit/discard/restriction/revocation races, changed terms and explicit reconfirmation, competing submits, full producer/deferred rollback, migration preservation and packaged runtime. Executed results and limits are in [verification](DRAFT_SUBMISSION_VERIFICATION.md); this design record alone is not test execution.
