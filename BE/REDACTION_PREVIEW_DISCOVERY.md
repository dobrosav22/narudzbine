## Source facts observed in the current code

- account_identity owns email, display_name, optional language, state, security/credential generations and profile revision. Permanent business_account binding must remain. Ordinary organization closure revokes sessions and closes/disconnects the organization, but does not set every account to DEACTIVATED; do not mistake closure alone for demonstrated account/provider authentication containment.
- A business_contact has organization ownership but no account/person foreign key. A contact whose name/email resembles the requester cannot be selected automatically. A reviewed explicit entity association is needed before proposing its redaction. Current contacts have original replay snapshots; unsharing/archiving is not deletion of shared history.
- purchase_order_event stores actor_display_name; order_message stores author_display_name and text. Other current order snapshots/replays/results, cancellation context, delivery/inbox caches and provider copies can retain text. Changing only account_identity.display_name cannot claim all historical copies were erased.
- The portable JSON projection has a carefully explicit source manifest and ordinary counterpart masks. Its source views are authorized EXPORT-job views, not a redaction-purpose grant. Do not reuse them to give a platform operator a commercial data export.
- Audit records/stock/order/message identities, money, quantities, original actor/account-organization/country bindings and commercial totals are retained. An explicit separately scoped privacy exception may redact approved fields under DESIGN_SPEC section8; ordinary HTTP roles still cannot rewrite append-only records.
- Global PLATFORM_EVIDENCE_V1 holds and disposal claims already serialize technical retirement. A redaction executor needs the same hold barrier plus current source/permission/containment guards, and coordination with the new archive spool/membership and already published encrypted evidence. A preview cannot substitute for those committing checks.
- The existing privacy_fulfillment table/counter is EXPORT-specific. REDACTION progress needs a disjoint source and safe state projection. Adding another PrivacyFulfillment bean without aggregation would make JdbcPrivacyCases.getIfAvailable ambiguous; fix the projection deliberately with disjoint case-kind ownership.

## Required preview shape and limits

A versioned fixed action catalogue must name actual supported fields and every retained/unsupported/provider/shared family. Start from the original requester identity, without inferring that every organization contact or free-text occurrence belongs to that person. Any explicit additional entity selection must be bounded, in the original organization/country and backed by the reviewed subject-association reference. No arbitrary table names, SQL, JSON paths, free-form field masks or content-by-string-matching. Source versions/immutable identities must invalidate stale execution; don’t expose raw values or low-entropy public content digests as preview data.

Preview reports authentication state/live sessions, sole-owner/closed-organization constraint, pending or uncertain credential/setup/recovery/delivery work, active holds, source bounds, archive coordination and the absence of requester/legal/containment attestations as explicit blockers. It may be prepared while blocked so the operator can see what remains; it must never silently deactivate an owner, alter organization membership, clear uncertain work or issue provider changes. Any human references supplied during local tests are clearly synthetic and establish no real legal fact.

Account-only work is not an organization-wide erasure result. Preserve scope and unresolved families in durable evidence; do not mark the whole case COMPLETED merely because one display name changed. No commercial/statutory purge or backup/WAL/provider deletion follows from the preview.

## Following execution dependency

After preview acceptance, implement the separate reviewed intent/commit/completion workflow as a coherent batch: stable case/sequence identity, immutable encrypted non-content intent verified independently before source mutation, a dedicated restricted committing role with current authenticated authorization and stale-plan/hold/containment checks, actual idempotent database outcome, then independent completion only after commit. Unknown outcome inspects the same identity. Pending completion may reconcile its actual committed source after the original session expires without a fake SYSTEM actor or repeated destructive changes. Actual provider/legal/custody/recovery release remains externally gated; local construction uses explicit synthetic fixtures.

Owner-containment follow-through: current validate_organization_owner requires an ACTIVE verified owner even when the organization is CLOSED, and the approved policy forbids sole-owner deactivation/removal before transfer. Do not relax that invariant to make a redaction fixture succeed. A sole-owner case must explicitly report OWNER_TRANSFER_OR_REVIEW_REQUIRED; ordinary closed-organization transfer may be unavailable. Preserve the permanent owner and treat an actually irreconcilable real case as reviewed/legal work, not an automatic identity rewrite. Successful synthetic non-owner cases can exercise the normal supported workflow independently. This is a discovered blocker, not a new user answer or authority for a closed-owner exception.
