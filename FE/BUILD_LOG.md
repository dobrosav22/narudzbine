### 2026-09-27 — USE_MOCKS wiring

What: `serviceProvider.ts` reads `process.env.USE_MOCKS ?? process.env.NEXT_PUBLIC_USE_MOCKS ?? process.env.EXPO_PUBLIC_USE_MOCKS` and treats anything except `"false"` as mocks ON. Each name is written out literally because Next and babel-preset-expo only inline env vars by exact text match. It also exports `createServices(useMocks)` for tests and `USE_MOCKS` so the UI can show a "Mock data" badge. With mocks off it logs one console warning.
Real stubs: `services/real/<service>.ts`, one per `AppServices` key. Every method is `async () => notImplemented('<service>.<method>')`, so each **rejects** (like a network failure) rather than throwing synchronously, and the error names the operation. The files were generated by `packages/core/scripts/generate-real-stubs.ts`, which never overwrites existing files. Re-run it after adding a service or method.
Verified: `pnpm verify:real-stubs` calls all 79 methods across 17 services with the flag off and asserts every one rejects with NOT_IMPLEMENTED. Both apps were also built with the flag off and screenshotted: each shows a "Backend not connected" error naming `catalogue.listProducts`, with no mock data and no retry.
Affects: 02 → "The service layer pattern" (same design; this records how it's implemented).

### 2026-09-27 — Price resolution precedence (01 §11 open question #1, PROVISIONAL)

What: Resolved for the frontend as follows. (1) Pre-discount price = buyer override, else the highest quantity tier reached, else base price. (2) Live promotions apply **on top of that, including on top of a negotiated override**. When several promotions apply, the single best one for the buyer wins, with no stacking. `fixed` = amount off **per unit**, floored at 0. A promotion is live when `isActive && startDate <= now <= endDate`. Tiers must have `minQty >= 2` (qty 1 is just the base price).
Why: 01 §3 says "promotion applied on top"; 04 lists "promotion → override → tier → base", which reads as the same order. No-stacking and per-unit fixed are my choices, not the docs'.
Lives in: `packages/core/pricing/resolvePrice.ts` (with tests). The mock order service snapshots `priceAtOrder` through the same function.
Affects: 01 §11, 04 → "Price resolution order". **Needs business confirmation before the backend implements it.**

### 2026-09-27 — Currency: env-driven, BAM default (supersedes the EUR placeholder)

What: `packages/core/config.ts` exports `CURRENCY`, read as `CURRENCY ?? NEXT_PUBLIC_CURRENCY ?? EXPO_PUBLIC_CURRENCY` (literal names, same inlining rule as USE_MOCKS; `USE_MOCKS` moved into the same file). The default is `BAM`. The value is upper-cased, and anything that isn't a 3-letter code throws at startup. `formatMoney()` defaults to it and formats via `Intl.NumberFormat`, so no symbol is hardcoded anywhere. `DEFAULT_CURRENCY` was removed. The currency vars are in both `.env.example` files and in turbo `globalEnv` (so a cached build can't keep the old currency). Tested: default, all three overrides, and a malformed code. Also verified end to end: a mobile export with `EXPO_PUBLIC_CURRENCY=EUR` renders €.
Blast radius found:
- Hardcoded: exactly **one** literal (`DEFAULT_CURRENCY = 'EUR'` in constants.ts), reached through `formatMoney` from 4 call sites (web catalogue ×1, mobile catalogue ×3). No hardcoded symbols, and no currency in seed strings.
- Currency *assumed* but still not parameterized:
  - **Seed price magnitudes** were chosen to be realistic in EUR (1 EUR ≈ 1.956 BAM), so as BAM they read at roughly half the real-world price. Fixed-promotion values (2, 1.5) have the same issue. Left unchanged pending a decision.
  - **Locale** is hardcoded to `en-GB` in `formatMoney`, which renders "BAM 19.60". A Bosnian locale would render "19,60 KM". Not parameterized.
  - **`roundMoney`** assumes 2 minor units. That's correct for BAM but not currency-aware (e.g. JPY has 0).
  - Hermes `Intl` output on a real Android device is unverified. Checked in Node, Chrome and Expo's web export only.
Affects: 04 → "Currency".

### 2026-09-27 — Localized display: LOCALE, bs-BA default (supersedes the en-GB note in the Currency entry)

What: `packages/core/config.ts` exports `LOCALE`, read as `LOCALE ?? NEXT_PUBLIC_LOCALE ?? EXPO_PUBLIC_LOCALE`, defaulting to **`bs-BA`** and validated with `Intl.getCanonicalLocales`. It's in both `.env.example` files and turbo `globalEnv`. UI copy stays English; this drives formatting only.
- **All** number/money/date display goes through core: `formatMoney`, `formatNumber`, `formatPercent`, `formatDate`, `formatDateTime`, `currencySymbol`. Screens never call `toLocaleString`/`toFixed`, and never hardcode "KM" (input adornments use `currencySymbol()`).
- **Discovered: Chrome lies about Bosnian.** `Intl.NumberFormat.supportedLocalesOf('bs-BA')` says yes, but Chrome's trimmed locale data has no Bosnian number symbols, so it silently formats English-style ("BAM 1,234.50"). Node formats correctly ("1.234,50 KM"), so unit tests alone missed it; the browser e2e caught it.
- **Fix**: `FORMAT_LOCALE` = `pickFormatLocale(LOCALE)`. It probes plain number output against English, and if the runtime lacks the data, falls back to a same-convention BiH locale (`bs` → `hr-BA`, then `sr-Latn-BA`). A currency-based probe doesn't work: Chrome's fallback adds a space ("€ 1,234.50"), which fooled the first attempt. `LOCALE` stays the setting; `FORMAT_LOCALE` is what's applied. Result everywhere: "19,60 KM", "5.000", "27. sep 2026."
- **Still unverified**: Hermes `Intl` on a real Android device. The same probe covers it either way.
- **Input parsing** (`parseDecimal` in core) accepts "19,60", "19.60", "1.234,50" and "1 234,50". Prefilled inputs use `toDecimalInput`, which formats without grouping so values round-trip.

### 2026-09-27 — Money rounding fix (bug found by e2e)

What: `roundMoney` (packages/core/pricing) used `Math.round((n + Number.EPSILON) * 100) / 100`. That fails on exact half-cents, because float products like 42,10 × 0,95 = 39,995 are stored as 39,99499999…, so the tier price showed **39,99 instead of 40,00 KM**. The EPSILON nudge is far too small at these magnitudes. The fix snaps the cents value to 12 significant digits before rounding half away from zero. There's now a regression test. **Every resolved price, line total and seed order snapshot goes through this function**, so under the old code some half-cent prices were under-charged by 0,01 KM.
